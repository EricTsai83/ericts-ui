React callback ref：把同一個 DOM 交給內部與外部

從 ref 為什麼能接收函式，到 React 19 的 cleanup：理解誰建立 DOM、誰保存它，以及誰負責釋放資源。

先看真正要解決的問題

假設你做了一個 SVG 邊框元件。元件要取得自己的 SVG，找到父元素、量測尺寸，才能畫出合適的邊框。使用元件的人也可能需要取得同一個 SVG，例如在按鈕事件中讀取它的範圍。這裡只有一個 DOM 元素，但有兩個使用者：元件內部，以及呼叫元件的外部程式。

React 元件是產生介面描述的函式；DOM 則是 React 提交更新時實際建立的瀏覽器物件。不能在 render 過程中假設 DOM 已經存在。ref 提供一個取得這個實際物件的管道。

ref 是一個接收 DOM 的位置

useRef 回傳帶有 current 屬性的物件。它會在重新 render 之間保持身分穩定。下列程式直接把物件交給原生 SVG，React 會在連接時設定 current，移除時清空。修改 current 本身不會要求 React 重新 render。 

TypeScriptconst myRef = useRef<SVGSVGElement | null>(null);

// 這裡的 svg 是原生元素，React 自己負責填入 myRef.current。
<svg ref={myRef} />

但寫成 <SvgFrame ref={myRef} /> 時，SvgFrame 是自訂函式元件。在 React 19，它能從 props 接收 ref，但仍必須明確把它接到真正的 DOM。只接收參數，不會自動讓外部拿到 SVG。

為什麼 ref 可以放一個函式？

這是 React 的 API 契約：原生元素的 ref 可以是 ref 物件，也可以是接收 DOM 的 callback。當 SVG 被連接時，React 呼叫 callback，將實際的 SVG 當作參數。這個函式不是 HTML 屬性，也不會以文字寫進 SVG；是 React 在提交階段處理的工作。 

TypeScriptfunction receiveSvg(element: SVGSVGElement | null) {
  console.log(element);
}

<svg ref={receiveSvg} />; // 交出函式，之後由 React 呼叫
// 不要寫 ref={receiveSvg()}，那是在 render 時立刻執行函式。

函式的名字並不重要，叫 receiveSvg、setRefs 都可以。重要的是它被放在 ref 這個位置，因此由 React 依 DOM 的生命週期呼叫。它不等於 click handler，也不能假定只執行一次。

setNode 與 assignRef 各自負責什麼？

setNode 是 useState 回傳的 setter，用來更新元件內部保存的 DOM。它會排程重新 render，而不是立刻改變目前函式中的 node 變數。在邊框元件裡，依賴 [node] 的 effect 因此能在節點就緒或改變時建立量測 observer。

assignRef 是作者自己寫的工具，不是 React API。它把同一個 DOM 轉交給外部傳入的 ref：物件形式就設定 current，函式形式就呼叫它。它本身不要求重新 render；但被它呼叫的外部 callback 可以有自己的行為。 

TypeScript// element 是 React 提供的同一個 SVG 物件。
setNode(element);              // 內部保存，讓依賴 node 的邏輯跟著更新
const cleanup = assignRef(ref, element); // 外部也取得同一個物件

外部的變數叫 myRef，傳入後內部參數叫 ref，兩個名字指的是同一個 ref 物件。這是普通的參數傳遞，不是另外建立一個 ref。保存到內外兩邊也不會複製 SVG。

完整範例：從傳入到取得 DOM

下面是可獨立閱讀的 React 19 範例，省略動畫與父元素量測。data-ready 用來示範內部 state 如何反映節點就緒；外部則透過按鈕讀取同一個 SVG。這裡刻意保留內部 state，供理解合併流程；若真實元件只需要外部 ref，直接傳給 SVG 即可。 

TypeScript"use client";

import { useCallback, useRef, useState, type Ref } from "react";

function assignRef<T>(ref: Ref<T> | undefined, value: T | null) {
  if (typeof ref === "function") {
    const cleanup = ref(value);
    return () => {
      if (typeof cleanup === "function") {
        cleanup();
      } else {
        ref(null);
      }
    };
  }

  if (ref) {
    ref.current = value;
  }

  return () => {
    if (ref) {
      ref.current = null;
    }
  };
}

function SvgFrame({ ref }: { ref?: Ref<SVGSVGElement> }) {
  const [node, setNode] = useState<SVGSVGElement | null>(null);

  const setRefs = useCallback((element: SVGSVGElement | null) => {
    setNode(element);
    const cleanup = assignRef(ref, element);
    return () => {
      setNode(null);
      cleanup();
    };
  }, [ref]);

  return (
    <svg ref={setRefs} width={120} height={40}
      aria-label="外框" role="img" data-ready={node !== null}>
      <rect x={1} y={1} width={118} height={38}
        fill="none" stroke="currentColor" />
    </svg>
  );
}

export default function Example() {
  const myRef = useRef<SVGSVGElement | null>(null);
  return (
    <div>
      <SvgFrame ref={myRef} />
      <button type="button" onClick={() => {
        console.log(myRef.current?.getBoundingClientRect());
      }}>讀取 SVG 尺寸</button>
    </div>
  );
}

讀取順序是：Example 建立 myRef → 把它傳給 SvgFrame 的 ref 參數 → SVG 建立後 React 呼叫 setRefs(svg) → setNode 保存給內部 → assignRef 將 SVG 填入外部的 myRef.current。等使用者點擊按鈕，事件處理器就能取得已連接的 SVG。

cleanup 為什麼必須傳回去？

React 19 的 callback ref 可以回傳清理函式。假設外部 callback 在拿到 SVG 時建立一個 observer，它就可以回傳 disconnect 的操作。React 會在解除該 ref 時執行 cleanup；這也可能發生在 ref 換成另一個函式時，不只元件卸載時。 

TypeScriptconst observeSvg = useCallback((element: SVGSVGElement | null) => {
  if (!element) return;
  const observer = new ResizeObserver(() => {
    console.log(element.getBoundingClientRect());
  });
  observer.observe(element);
  return () => observer.disconnect();
}, []);

<SvgFrame ref={observeSvg} />;

如果 wrapper 只呼叫 ref(element)，卻丟掉回傳值，React 只看見 wrapper，無法知道內部 callback 建立了什麼資源。範例中的 assignRef 把清理行為包成函式回傳；setRefs 再把包含內部重設與外部清理的函式交給 React。

這個合併流程分成三種情況：外部 callback 有回傳 cleanup，就執行它，不另外傳入 null；callback 沒回傳 cleanup，就在解除時呼叫 ref(null)；外部是物件 ref，就把 current 清成 null。沒有外部 ref 時，仍可正常執行內部邏輯。

元件內部 effect 建立的 ResizeObserver，與外部 callback ref 建立的資源，是兩套生命週期。effect 的 return () => observer.disconnect() 只清理自己的 observer，不會自動處理外部 callback 的回傳值。

useCallback 與 StrictMode：避免重連，也容許重連

每次 render 都直接建立新的 ref 函式，React 會視為 ref 改變，解除舊 callback 再連接新的。這不一定是錯，但若 callback 更新 state 或建立 observer，就可能導致反覆重連。用 useCallback(..., [ref]) 可以在外部 ref 沒變時保持函式身分穩定。外部 ref 真正換掉時，則必須清理舊 ref，再把 DOM 交給新 ref，不能為了穩定而省略依賴。

開發模式的 StrictMode 會額外檢查 callback ref 的 setup 與 cleanup。正確的實作應能承受「建立 → 清理 → 再建立」，最後只保留一份有效資源，卸載後歸零。不要靠「只執行第一次」的旗標跳過這個檢查。

什麼情況值得這樣設計？

當元件內部確實需要 DOM，而外部也需要取得相同 DOM，使用 callback ref 合併是合適的做法。若節點的變動還需要驅動 effect，內部以 state 保存它也有理由：單純修改 useRef.current 不會觸發 effect。

若只有外部需要 DOM，直接使用 <svg ref={ref} /> 更簡單。若內部只在事件中讀取 DOM，不需要因節點變更重新 render，可以考慮內部 ref，避免額外 state 更新。不要為每個 DOM 都加入合併工具，也不要在 render 中執行量測或依賴尚未提交的 ref。

在 ericts/ui 的 StrokeTraceBorder 中，內部需要找到 SVG 的父元素來量測邊框，外部則能接收 SVG DOM。合併 callback 因而符合需求。此次修正保留這個結構，補齊外部 cleanup 的轉交，並測試 ref 替換、卸載、物件 ref 清空，以及 StrictMode 的資源平衡。
